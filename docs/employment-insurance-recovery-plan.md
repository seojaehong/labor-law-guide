## 백업·교정·롤백 순서 — 아직 실행하지 않음

1. 공식 전문 원본을 staging에 보관한다. 요청 MST/efYd, 응답 법령 기본정보, 조문/별표/부칙, 원본 순서, 수집 시각, 원문 SHA256를 manifest로 묶고 누락/잘린 응답은 거절한다. API 인증값은 기록하지 않는다.
2. staging의 모든 법령 행을 corpus166행과 대조한다. 조문키/가지번호·순서·장절·삭제/별표 구분·본문·시행일 및 부칙을 비교하고, 조문 actual 시행일과 snapshot 시행일을 혼동하지 않는다. 공식법령의 구조가166행과 다르면 무리하게 맞추지 않고 차이를 검토한다.
3. 운영 변경 직전에 고용보험법 전체166행의 정확한 before-image를 제한된 로컬 보관 위치 .local-backups/pr54-insurance/<UTC시각>/before.json에 export한다(모든 변경 대상 컬럼 및 embedding/embed_input_len 포함). 디렉터리0700·파일0600, git 미추적·외부 API 미전송으로 보관한다. 원문·백업·대조 결과 해시와 대상id/변경 전후 값을 기록한다. 감사 hash manifest만으로 이 단계를 대체하지 않는다. 백업을 저장·복원 검증하지 못하면 UPDATE하지 않는다.
4. 검증된 차이만 단일 transaction에서 반영한다. 대상id·법명·구분·변경전 행 hash가 감사 기준과 맞지 않으면 전체 중단한다. unrelated 법령과 PR24 작업은 건드리지 않는다. 본문이 바뀐 행의 기존 embedding을 그대로 유효하다고 사용하지 않는다. 새 유료 임베딩 호출은 하지 않으며 무효화 범위를 별도로 명시한다.
5. 같은 transaction에서 대상 수·현재판 source·본문/날짜·삭제/중복 invariants를 검사한다. 위반 시 commit하지 않고 rollback한다. commit 이후 복구가 필요하면 after-image hash를 대조한 대상 행만 before-image로 되돌려 동시 타인 변경을 덮지 않는다. 본문과 벡터를 함께 복원하고 최종 row hash를 검증한다. 새로 추가된 행이 있다면 manifest의 새id만 별도 복원 대상으로 다룬다.
6. 읽기 재조회와 키 없는 회귀검사로 제40/45/70조의 실제 참조·정확한 source snapshot 및 미래판 보류를 확인한 후에만 데이터 장애 해소로 판단한다. 검사 기준일과 사건 발생일·경과규정 검증은 계속 구별한다.

미래판을 같은 테이블에 단순 추가하면 현재 게이트의 conflicting_revisions가 발생한다. 검증용 현행 snapshot 하나를 유지하거나 명시적인 버전 선택 구조를 별도 검토해야 하며 임의 최신판 선택·날짜 우회는 하지 않는다.
