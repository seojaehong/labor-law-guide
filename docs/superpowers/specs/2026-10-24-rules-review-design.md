# 기관 규정 정비 점검 — 1단계 설계 (2026-10-24)

## 1. 왜 만드나

공공기관·대학·지방공사는 3,000만~1억 6,000만 원을 들여 6~8개월짜리 「제규정 정비 용역」을 맡긴다. 나라장터에서 2023~2026년에 나온 기관 전체 정비 용역은 21건이다(작업 폴더 `_30_컨설팅/2026/규정정비_나라장터/05_요약_261023.md`). 용역 노동의 상당 부분은 규정을 하나하나 읽고 서로 맞춰 보는 일이다.

재홍님 목표(261023~24): 원래 이 용역을 맡기려던 기관의 규정 담당자가 규정 전체를 zip 하나로 올리면, 결과물까지 한 번에 받는다.

- 결과물은 **결재에 올릴 개정안**이다. 그대로 올릴 수는 없으므로 확인 과정까지 서비스 안에 둔다.
- 규정 담당자가 전부 확인하고, 그 과정에서 소관 부서 의견을 묻는다. 의견이 다르면 조율하는 것도 담당자 몫이다.
- 범위는 **기관 규정 전체**다. 규정은 서로 인용·위임하고 같은 용어를 쓰기 때문에 일부만 볼 수 없다. 단계는 나눠도 된다.
- 첫 단계 합격선: 규정 전체에서 서로 연결된 곳을 점검하고, 바꿀 사항을 반영해 정리한다. 수준은 **과업지시서가 요구하는 품질**이다.

## 2. 제품 지도 자리 (개발게이트 G0)

`NOW.md` 제품 지도의 다섯 영역(급여·산업안전·괴롭힘·연차·감독 제출)에는 「기관 규정 전체」 영역이 없다. 이 기능은 **취업규칙 점검의 확장**으로 붙인다. 공통점은 「기준 문서와 대상 문서를 맞춰 본다」는 대조 구조다.

다만 회계·계약·학사 규정은 노무 밖이다. 1단계는 규정끼리 대조만 하므로 분야를 가리지 않는다. 그래도 지도 밖으로 나간다는 점은 여기와 최종 보고에 적어 둔다.

- 지금의 대안: 외부 용역에 맡기거나, 담당자가 엑셀과 메일로 직접 한다.
- 증거: 나라장터 발주 21건, 같은 종류 용역의 입찰 준비·수행 경험(내부 기록).

## 3. 1단계 범위

### 하는 것

1. **올리기**
   - zip 하나 또는 파일 여러 개를 받는다. 형식은 hwp·hwpx·docx·txt다.
   - zip 안의 zip은 한 단계만 푼다. 윈도우 압축의 한글 파일 이름(EUC-KR)을 읽는다.
2. **같은 규정 묶기**
   - 파일 이름을 정리해서 같은 규정을 하나로 묶는다. 지우는 것은 분류번호 `2-3-18`, `(20231103)_일부개정` 같은 꼬리, 공백, 기관 이름이다.
   - 같은 규정이 여러 파일이면 hwpx, hwp, docx, txt 순서로 하나만 읽는다. 읽지 않은 파일은 올리기 요약에 보여 준다.
   - pdf와 그림은 1단계에서 읽지 않는다. 읽지 않는다는 사실을 화면에 적는다.
3. **규정 간 대조**(과업 요구 빈도순)

   | 종류 | 무엇과 무엇을 맞추나 | 고친 문안 |
   |---|---|---|
   | 다른 규정 인용 | 「○○규정」이 묶음 안 규정 이름과 같은지 | 이름이 비슷한 규정이 하나뿐이면 바꿀 이름을 제안 |
   | 조문 인용 | 「제N조」·「제N조제M항」이 인용 대상 규정에 있는지 | 조문 제목이 함께 적혀 있고 그 제목이 다른 번호에 있으면 번호를 제안 |
   | 위임 | 「○○규정(세칙)으로 정한다」의 대상이 묶음에 있는지 | 없음(대상 규정 확인) |
   | 상위 규정 | 「○○ 시행세칙」의 상위 「○○」가 묶음에 있는지 | 없음 |
   | 별표·별지 | 본문이 부르는 별표·별지 서식이 규정 안에 있는지, 실린 별표를 본문이 부르는지 | 없음 |
   | 조문 체계 | 조 번호 빠짐·겹침, 항 번호(①②…) 빠짐 | 없음 |
   | 정의 용어 | 정의 조문의 같은 용어가 규정마다 다르게 정의됐는지 | 없음(양쪽 원문만) |
   | 알기 쉬운 표현 | 법제처 「알기 쉬운 법령 정비기준」의 바꿀 말 | 바꿀 말(일괄 반영 가능) |
   | 개정 표시 형식 | 날짜가 깨진 표시(`[2015.0130개정]`), 법령 표기 방식(`<개정 2023. 9. 1.>`)이 아닌 옛 모양 | 없음(규정마다 한 항목) |
   | 항 번호 글자 | 모양만 같은 다른 글자(`➂`)로 적은 항 번호 | 「③」으로 |
   | 같은 사항 다른 기준 | **규정과 그 시행세칙 사이**에서 제목이 같은 조문의 숫자가 다른지 | 없음(양쪽 원문만) |

4. **확인 작업대**
   - 항목마다 원문 발췌(걸린 글자 강조), 상대 조문 원문, 고친 문안(편집 가능), 결정, 사유를 둔다.
   - 결정은 반영·보류·해당 없음이고, 기본값은 늘 「미확인」이다.
   - 묶어 보기는 두 가지다. 규정별로 보면 담당자가 일하는 단위가 되고, 종류별로 보면 같은 종류를 일괄 결정할 수 있다.
   - 진행 수치를 보여 주고 키보드로 움직인다(J/K 이동, 1/2/3 결정).
5. **소관 부서 의견**
   - 규정마다 소관 부서를 정한다. 본문에 「담당부서」가 적혀 있으면 그 값을 기본값으로 쓴다.
   - 부서별 의견 요청 엑셀을 내보낸다. 항목 번호·현행·고친 문안·사유를 담고, 의견(동의/수정/반대)과 내용을 적을 칸을 둔다.
   - 회신 엑셀을 다시 올리면 항목에 의견이 붙는다. 수정·반대 의견은 「이견」으로 표시되고, 담당자가 조율 결과를 적는다.
6. **결재 묶음**
   - 신구조문대비표(docx): 열은 「현 행 | 개정안 | 사유」다. 반영 항목이 든 조문만 싣고, 고친 곳에 `<개정 YYYY. M. D.>`를 붙이며, 끝에 부칙(시행일) 줄을 단다.
   - 정비 검토표(xlsx): 전 항목과 결정·사유·부서 의견·조율 결과를 담는다.
   - 보류 목록과 부서 협의 내역은 신구조문대비표 문서 뒤에 붙인다.
   - **개정안 반영본(hwpx)**: 원본이 hwp·hwpx인 규정은 반영한 글자 고침을 원본 파일에 넣어 hwpx로 내보낸다. 기존 `src/lib/hwp/apply.ts`의 낱말 치환 경로를 쓴다. 표·그림이 섞인 문단은 자동 반영하지 않고 「직접 고칠 곳」으로 남긴다.

### 하지 않는 것(1단계)

- 상위법령 대조(2단계): 인사노무 분야부터, 취업규칙 정밀 점검 엔진을 다시 쓴다.
- 규정 통폐합 제안, AI가 지은 조문, pdf·그림 읽기, 서버 저장, 부서별 링크 공유.

### 하면 실패인 것

- 「진단·자문·판정」으로 읽히는 말. 과업지시서에 「진단」이 있어도 화면에는 쓰지 않는다. 쓸 말은 점검·대조·확인·정리다.
- 걸린 곳이 0건인 종류에 「문제 없음」이라고 쓰는 것. 「이 대조에서 걸린 곳 없음」으로 쓴다.
- 안전한 치환이 없는 종류에 문안을 지어내는 것.
- 반영을 미리 찍어 두는 것.

## 4. 상태어 (개발게이트 G2)

| 말 | 무엇과 무엇을 비교한 결과인가 | 이것이 아니다 |
|---|---|---|
| 걸린 곳(항목) | 규정 글자와 다른 규정 글자(또는 정비기준 낱말표)를 맞춰 어긋난 자리 | 위반·하자 판정 |
| 미확인 | 담당자가 아직 결정하지 않음 | 문제 없음 |
| 반영 | 담당자가 고친 문안을 개정안에 넣기로 함 | 확정된 개정(결재 전) |
| 보류 | 지금 개정안에서 빼고 따로 남김(사유 필수 권장) | 해당 없음 |
| 해당 없음 | 기관 사정상 그대로 둠(의도된 차이) | 점검 오류 신고 |
| 부서 의견 동의/수정/반대 | 소관 부서가 고친 문안을 보고 남긴 회신 | 담당자 결정 |

| 조율 결과 | 이견을 담당자가 정리한 글 | 부서 동의 |
| 이 대조에서 걸린 곳 없음 | 해당 종류의 대조를 돌렸고 걸린 자리가 없음 | 규정이 옳다는 확인 |

## 5. 어떻게 만드나

- **위치**: labor-law-guide 사이트의 `/tools/rules-review`.
- **처리 위치**: 파일 읽기와 대조를 모두 브라우저 안에서 한다. 규정 파일은 서버로 가지 않는다.
- **읽기**: hwp·hwpx는 rhwp 문단 색인(`HwpEditDoc.paragraphs` → `toLines`)으로 읽는다. 그래야 항목의 글자 위치를 그대로 반영본 고침(`applyChanges`의 `word`)에 쓸 수 있다. docx는 `doc-io`와 같은 방식으로 문단을 읽는다.
- **항목 번호**: `종류|규정|조문|발췌`로 정해지는 해시라서, 같은 파일을 다시 올려도 결정이 살아남는다. 부서 의견 엑셀도 이 번호로 다시 붙는다.
- **저장**: 브라우저 IndexedDB에 자동 저장한다. 「작업 파일 저장/열기」(.json)로 다른 PC에 넘기거나 백업할 수 있다.
- **코드**: `src/lib/rules-review/` 아래에 읽기·정리·대조·묶음을 둔다. 취업규칙 `precise/articles.ts`에는 파이썬 쌍둥이가 있으므로 고치지 않고, 조문 머리 정규식만 같은 모양으로 쓴다.

### 바꾼 결정 (채팅 기본값과 다름 — 내 판단)

1. 채팅에서는 「기관별 분리 보관」이라고 했다. 이를 **브라우저 안 처리 + 작업 파일**로 바꿨다. 비공개 규정이 서버로 가지 않으므로 기관 보안 심사 부담이 줄어든다. 대신 여러 사람이 동시에 보는 일은 안 된다.
2. 채팅에서는 「부서는 링크로 들어와 의견」이라고 했다. 이를 **부서별 엑셀 내보내기·가져오기**로 바꿨다. 서버 저장이 없으면 링크를 만들 수 없다. 엑셀은 담당자가 지금 일하는 방식(엑셀+메일)과 같다. 링크 방식은 2단계 후보다.
3. 채팅에서는 결재 묶음을 「한글(hwpx)」로 낸다고 했다. 실제로는 **신구조문대비표는 docx**로 내고, **반영본은 hwpx**로 낸다. 신구조문표를 쓰는 기존 부품(`compareDocx`)이 docx용이라서다. docx는 한글에서 열린다. 표까지 hwpx로 내는 일은 후속이다.

### 검토자 질문에 대한 내 판단 (builder-check 261024)

1. **편집 단위**
   - 고친 문안이 있는 종류는 걸린 글자만 바꾼다. 이 경우 반영본에도 들어간다.
   - 고친 문안이 없는 종류도 「반영」할 수 있다. 이때 담당자가 조문의 개정 문안을 직접 쓰면 그 문안이 신구조문대비표에 실린다. 반영본에는 넣지 않고 「직접 고칠 곳」 목록으로 남긴다.
2. **같은 규정의 여러 판**: 파일 이름이나 본문 「최근개정」의 날짜가 가장 늦은 판을 읽는다. 올리기 요약에 「다른 판 N개 — 읽지 않음」을 보여 준다.
3. **별표·별지 따로 파일**: 이름에 「별표」·「별지」가 있고 앞부분이 어떤 규정 이름과 맞으면 그 규정에 붙인다. 맞는 규정이 없으면 「붙일 곳 모름」으로 보여 준다.
4. **신구조문대비표**
   - 한 문서에 규정마다 표 하나씩 싣는다. 제목은 「○○규정 신·구조문대비표」다.
   - 시행일은 결재 묶음 화면에서 받고, 비워 두면 「○○○○. ○. ○.」로 둔다.
   - 개정 표시는 법령 표기 방식 `<개정 YYYY. M. D.>`로 쓴다. (교정 261024) 처음에는 「기관에서 가장 많이 쓴 모양」을 따르려 했다. 그런데 대학 A 실측에서 가장 많은 모양은 옛 표기 `[2013.12.20.개정]`이었고, 최근 개정분은 이미 `<개정 …>`으로 바뀌어 있었다. 다수결을 따르면 옛 표기로 되돌리게 되므로 기준을 법령 표기 방식으로 바꿨다.
   - 고친 글자는 현행·개정안 양쪽에 밑줄을 긋는다.
5. **실데이터**: 로컬에 있는 한 대학(이하 「대학 A」)의 규정 묶음을 쓴다. hwp 24개와 pdf가 있고, 하위 폴더에 같은 규정이 한 번 더 들어 있다. 저장소에는 넣지 않으며 기관 이름도 적지 않는다(공개 저장소).
6. **알기 쉬운 표현 낱말표**: 법제처 정비기준에서 **문맥과 관계없이 바꿀 수 있는 말만** 골라 만든다(예: 당해→해당, 익일→다음 날, 기타→그 밖의). 문맥을 타는 말은 넣지 않는다.

## 6. 합격 확인

### 결과 (261024)

- **단위 시험**: 27건이 통과했다. 심은 결함 11종을 모두 잡았고, 깨끗한 규정에서는 0건이었다. 같은 파일을 다시 올려도 항목 번호가 같았다. 부서 의견 엑셀 왕복, hwpx 반영본, EUC-KR zip 이름도 확인했다.
- **대학 A 실측**: 규정 24개를 브라우저에서 4.4초에 읽었다.
  - 항목은 157건이다. 종류별로 보면 알기 쉬운 표현 109, 개정 표시 19, 항 번호 글자 다름 10, 묶음에 없는 규정 7, 조 번호 빠짐·겹침 5, 없는 조문 인용 2, 본문이 부르지 않는 별표 3, 항 번호 빠짐 1, 이름 표기 1이다.
