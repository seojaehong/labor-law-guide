# 취업규칙 정밀 점검(C) 저비용 파이프라인 — 설계

2026-10-21 · 재홍님·로컬 세션 합의분

## 왜

- C(/취업규칙검토 스킬)는 A(/laws 브라우저 점검)가 못 잡는 것을 잡는다 — 기간 밖 기존 법 문제, 괴롭힘 조항 부실(10/5 실측), 종전 규칙 대비 불이익변경·운영 불능 조항(10/21 드리븐 실측).
- 그러나 에이전트 루프라 건당 $3.3~4.5(Opus 5.5)였고 비용 대부분이 캐시 읽기였다. 모델만 바꿔서는 15%밖에 안 준다.
- 재홍님 방향: **laya + Haiku 조합**으로 비용을 낮춘다.

## 결정

1. 에이전트 루프를 **고정 파이프라인**으로 바꾼다. LLM은 필요한 단계에만 쓴다.
2. 단계
   - ① 조문 분할·짝짓기(종전/개정안 두 문서 또는 한 문서) — LLM 없음
   - ② 법령·표준 매핑 후보(`scripts/laws/work_rules_map.json`, 본문 검색) — LLM 없음
   - ③ 수치 비교(일·주·개월·년·시간·%) — 종전보다 줄어든 수치를 불이익변경 신호로 — LLM 없음
   - ④ 조문별 1차 분류 — **Haiku 5.5**(`claude-haiku-5-5`), 조문 하나씩, 구조화 출력. 「문제없음」은 확신할 때만, 나머지는 위로 올린다
   - ⑤ 판단 — ④에서 올라온 조문만. **판단 백엔드는 교체 가능**(laya 자리). laya 의 정체가 확인될 때까지는 Anthropic 모델 백엔드로 돌린다
   - ⑥ 산출 — 표준 열 대조표 JSON(`comparison.v1`) + 검수용 md
   - ⑦ 노무사 검수 — 사람
3. 산출 표준 열(10/14 UX 총정리와 같다): 조문 / 현행 / 개정안 / 개정 사유 / 근거·시행일 / 불이익변경 / 점검 결과 / 운영 메모
4. 점검 결과 4분류(드리븐 고객 의견 4): `현행 수정 필요` · `시행 예정` · `회사 선택` · `추가 확인`
5. 단계별 토큰·비용을 기록한다. 정답지 3건(쿠우쿠우 강동 신고본·드리븐 261021·표준 2023판 Opus C 결과)으로 Opus C 대비 놓친 항목과 건당 비용을 잰다. 정답지와 고객 원문은 **로컬 전용**이고 레포에 넣지 않는다.

## 변경 (2026-10-21 저녁) — laya 대신 판단 모델 API

재홍님 「라야는 못 돌리고 jev api 로 가야 할 것 같아 · 지피티에도 디시젼 모델이 있다」.

- 1차 분류(④)를 **교체 가능한 백엔드**로 만들고 셋을 같은 정답지로 비교한다: Haiku 5.5(구조화 출력) · **Jev**(TypeSafe `POST https://api.typesafe.ai/v1/systemone`, `jev-latest`, 질문 `noul`·`choice`·`score`, 확률·confidence 반환) · **OpenAI Decisions**(`POST /v1/decisions`, `gpt-6-luna`, 질문 `predicate`·`choice`·`score`, 2026-10-06 공개 베타)
- 판단 모델은 글을 쓰지 않는다. 「위로 올릴지」만 확률로 정하고, 글(사유·제안 문안)은 올라온 조문에만 LLM 판단 단계(⑤)가 쓴다
- 우리 데이터 기준 Jev 실측(2026-10-06): 후보 중 고르기 7/8 · 12라벨 분류 55%. 그래서 1차 분류 질문은 라벨 하나를 고르게 하지 않고 **예/아니오 확률 질문 여러 개**로 쪼갠다
- 단가(입력 1M 토큰): Jev $0.042(외부 실측 cmdspace 기록 — 청구서로 재확인 필요) · gpt-6-luna $0.10(가이드: 출력·캐시 과금 없음, 가격표에는 출력 $0.50 — 첫 실측 청구로 확인)
- 키: Jev = 서버1 `work-orchestrator/.env` 에만 있다. OpenAI = 서버1·로컬 어디에도 없다. 로컬 openai SDK 2.28.0 에는 `decisions` 가 없어 올려야 한다
